# FINDING — `e33_logit_v2` does not reproduce, and the repro MODULE is wrong, not the stored result

**Status: LOCAL cause, rung "argv reconstruction". Found by the 2026-08-29 T1 sweep, module 10 of 22.**
**No stored science is invalidated. One repro module is mis-specified and must be corrected.**

## What happened

`e33_logit_v2` returned `MOVED_RC1`: payload `73b90a8b5d582481 -> 69faeffafcdd0a5d`, **86 numeric
fields changed**, and the experiment's own VERDICT string flipped:

```
stored : I INSIDE THE CORPUS SPREAD — 1 of 5 corpora fit an operator that is NO BETTER
         than not fitting at all. The crossover exists on the CORPUS axis.
rerun  : I BELOW ALL FIVE — the fitted operator helps at 410M regardless of corpus;
         the corpus floor is a floor on a real advantage
```

A flipped verdict is the most serious outcome this sweep can produce, so it was diagnosed before
anything else proceeded.

## Root cause: `--band` is documented inclusive and implemented exclusive

`experiments/t33_logit_baseline.py`, two lines of the same file:

```python
52:  ap.add_argument("--band", default=None, help="lo,hi inclusive; default = 0.35-0.85 depth")
81:  BAND = ([int(x) for x in range(*[int(v) for v in a.band.split(",")])] if a.band
```

The help says **inclusive**. `range(9, 21)` is **exclusive**. So `--band 9,21` yields twelve
layers, not thirteen:

| | band | layers |
|---|---|---|
| stored result | `[9,10,...,20,21]` | **13** |
| this re-run, via `--band 9,21` | `[9,10,...,19,20]` | **12** |

Everything downstream follows from that one missing layer. The derangement is a permutation of the
band, so a 12-layer band produces a completely different map (`{9:17, 10:9, ...}` vs
`{9:12, 10:13, ...}`) — not a perturbation of the stored one, an unrelated one. Every score
computed through it differs, and the verdict flips.

## Why the stored result is the correct one

The canonical band everywhere else in this repository is thirteen layers:

```
experiments/t59_read_dose.py     BAND = list(range(9, 22))
experiments/t38_jgeometry.py     BAND = list(range(9, 22))
experiments/cv3_margins.py       BAND = list(range(9, 22))
experiments/d3_corpus_by_family.py  BAND = list(range(9, 22))
```

`list(range(9, 22))` == `[9..21]` == the stored result's band. The stored `e33` is on the
repository's standard band. **It is the re-run that is on the wrong band.**

## Why this module and no other

`results/e33_logit_baseline_410m_v2.json` carries **no provenance block** — it predates
`provenance.py` (commit `1a6f5df`, 2026-08-14 20:05 PDT). It therefore has no recorded `argv`, so
`repro/exp/e33_logit_v2.sh` could not be generated by `tools/emit_exp_modules.py` and was
**hand-written from the script's own documentation**. The author read `help="lo,hi inclusive"` and
wrote `--band 9,21`. The help was wrong.

This is precisely the risk SPEC §2 pre-registered:

> **NONE** — no provenance block ... **these are the risk.** Their repro modules were hand-written
> from the scripts' own defaults, not from a recorded `argv`. ... If anything fails, look there first.

It is also the exact failure `repro/exp/_lib.sh` names in its own header — "the flags are
load-bearing -- `--band 9,21` vs the 0.35-0.85 default is [9,21] vs [8,20]" — which shows the
author believed `--band 9,21` produced `[9,21]`. It does not.

## Blast radius: this module only

`grep -l -- --band repro/exp/*.sh` matches `e33_logit_v2.sh` and `e52_factorial.sh`, but
`e52_factorial.sh`'s occurrence is in a comment: its executed invocation is
`--device cpu --workers 6 --rstrip --out ... --cells-out ...`, with no `--band`, and it matches
`provenance.argv` exactly. `e62_ladder1b_band.sh` and `e61_randomized_null.sh` are T2 and out of
scope for this sweep. **`e33_logit_v2` is the only affected module.**

## The fix — NOT applied, per SPEC §1.3

SPEC §1.3 forbids re-running with different flags to obtain a friendlier number, so this sweep
records the failure and stops there. The correction is for the operator to approve:

```diff
-    --model 410m --band 9,21 --device cpu \
+    --model 410m --band 9,22 --device cpu \      # range() is exclusive; 9,22 == layers 9..21
```

Better still, fix the defect rather than work around it: make line 81 inclusive
(`range(lo, hi + 1)`) so the flag matches its documentation, and correct every caller. That is a
change to experiment code and must not be made mid-sweep.

Until then `e33_logit_v2` should be reported as **DOES NOT REPRODUCE — module mis-specified**,
with the stored result standing.

## What this vindicates

The sweep found a latent defect that eight green gates did not: `test_band_rule` "asserts one band
rule against the bands on disk and says nothing about whether that band is the right one"
(CLAUDE.md §2.3), and it passed throughout. Re-running the experiment end to end is what exposed
the mismatch between a module's flags and the run they claim to reproduce.
